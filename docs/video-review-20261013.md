## 原 0.2.1 深审记录（修复前）

项目值得展示的主线是：**openKylin 3.0 实机 → 两款真实 Agent → 六类案例 → 自动评分 → 双 Agent 雷达图 → 案例与证据回溯**。CLI、工作台、发行包、结构化报告和隔离重复入口均已实现，当前安装及跨平台 CI 已有通过记录。

但本次进一步审查复现了两个 **P1 评分可信度问题**，正式录制评分结果前应先修正：回答检查没有限定查询回合，CLI 答复解析可能误取元数据。以前 158 项测试及安装验收通过，说明当时覆盖的工程路径可运行，不能证明这两个未覆盖的语义路径正确。当前 0.2.1 不宜直接沿用旧稿宣称评分完全准确、官方满分或真实长期稳定。

本轮没有修改操作系统、评分器或 Agent 适配器，没有启动云端真实对话；只读预检显示 KylinBot/OpenClaw 均 ready，blocked 为空，turns_started 为 0。它检查命令与存储存在，不能证明网关额度、认证和网络在录制时必然可用。

## 要求与展示重点

用户提供的命题 PDF 第 2 页交付 e 要求：openKylin 桌面、至少两款不同智能体运行评测、产生多维对比雷达图、完整录屏，建议 3–5 分钟。[官网参赛指南](https://www.oschina.net/os2026/)另要求视频展示核心功能与使用流程。

PDF 数据设计与自动评分各占 25%，因此视频应把最多时间留给具体案例、自动评分理由和可追溯证据，而不是罗列安装命令和自评分文件。

## P1：回答检查混用了不同对话回合

位置：`kmb/scoring.py` 的 `_evaluate()`，第 62 行起。`answer_contains` 在任意 assistant 回合中查找目标词，`answer_not_contains` 则要求所有 assistant 回合都不含禁止词。

复现一：`quick-update` 中先正确确认 Room A，再更新为 Room B，最后回答 Room B；即使有正确更新与召回事件，也因最早的确认文字出现 Room A 被判 fail，得分 2/3。

复现二：`quick-retention` 中第 1 回合确认 Atlas，第 2 回合明确回答不知道项目；提供正确存储召回事件后，最终答复仍被判 pass、1.0，因为 Atlas 曾出现在前面的确认句中。

建议：为回答检查显式定义目标回合或查询阶段。动态更新和召回检查对应最终查询，敏感信息全程禁止泄露的检查仍应保留全程语义。新增正常确认旧值、最终查询错误、明确全程禁词的回归案例，不能简单把所有检查都强制改成最后一轮。

## P1：CLI 答复解析可能把工具元数据当回答

位置：`kmb/agent_adapters/base.py` 的 `extract_text()`、`_find_text()`，第 143/162 行起。逐行解析及反向递归任意字典字符串，未可靠区分有效回答与工具/模型元数据。

最小复现：`{"result":{"payloads":[{"text":"The venue is Room B"}]},"meta":{"tool":"edit"}}`，期望提取回答，实际提取 `edit`。本轮已归档的 OpenClaw `quick-update` 第 1、2 回合 assistant 事件也记录为 `edit`；第 3 回合记录包含大段 JSON 元数据与最终可见文本，表明这不是只存在于假设输入的问题。

建议：先尝试完整 JSON，再按已验证的响应 schema 提取 assistant payload；支持真实格式化 JSON/JSONL，明确排除 meta、工具说明和模型字段。没有 assistant payload 时标为缺少可观测回答，不能拿任意字符串补位。修正后需要新的真实样例；不能仅重算已经丢失正确答复的旧 evidence 来宣称问题解决。

复现证据：工作区 `runs/video-script-review-20261013/review-probes.json`。原始结果和分数保留，不回写历史样本。

## 录制方案还需要纠正的地方

- 旧 `demo-script.md` 的“官方 100/100”叙事混淆工程自评与赛事评分，应删除该卖点。
- `demo-smoke.yaml` 只有长期保持、任务复用两类案例，不能把它的雷达图称作六类完整实测；主录制选 `quick.yaml` 六案例。项目主覆盖清单中的 49 条也不等于本次两款 Agent 都跑过 49 条。
- GUI“开始快速对比”默认采用日常 HOME；本次主录制使用已有 `official-repeat --isolated-home` CLI，再用同一工作台浏览生成的结果。没有单独准备隔离环境时，不用日常记忆做主录制。
- 现有 `record_desktop_demo.sh` 只录画面，不录麦克风；默认 1280×720、15fps、固定时长。不能承诺它生成有旁白的完整视频，也不要让定时结束截断真实评测。
- 六案例只是跨轮次的短任务，不能据此宣称跨数天的长期记忆验证。固定 seed 也不能保证远程模型完全确定。
- 屏幕上的“案例成功率”是案例通过比例，`score_valid` 是是否具备有效评分条件；二者不能混用。结构 strict 通过也不能自动证明语义评分正确。

## 正式录制前的门禁

1. 修正两个 P1 问题，并通过新增语义/真实 JSON 格式回归；记录修正后的项目版本或提交及评分器哈希。
2. 在不改变 openKylin 3.0 系统版本的条件下，用新版本执行至少一批 KylinBot/OpenClaw 六案例隔离评测；两侧应 `score_valid=true`、strict 校验通过、运行错误数为 0。
3. 用这批同一运行目录预演“运行历史 → 查看 → 结果中心 → 案例 → 证据”。不预填分数，不把旧批次充作新版本现场结果。
4. 录制恢复后，按届时实际版本、界面和有效运行证据重新准备稿件。新的有效低分可正常展示；缺凭据、超时、解析失败等运行错误应处理后再正式录制。

优先保留完整连续原始录屏。3–5 分钟是命题建议；如果网络等待使视频超过 5 分钟，应优先完整真实流程。可另做只加速等待部分的展示版并标注倍速，保留原片；任务书未明确认可剪辑方式，不以精简片替代完整原片。
